# v2方案

## 一、V2 定位

把 MeetMind 从"单场会议行动项提取器"升级为带独立证据裁决、可量化评估、可断点恢复的会议行动项 Agent。

核心原则不变：证据可追溯优先于摘要流畅，人工确认优先于自动执行。V2 增加三件事——一个独立的核验 Agent、一套可量化评估闭环、一组测量驱动的容错与性能优化。

明确排除：账号、多租户、数据隔离、计费、OAuth 登录

---

## 二、V2 要解决的真实痛点

V1 的证据校验是后端确定性规则：拒绝不存在的段落 ID、校验字段类型、负责人基础校验。但它挡不住语义层面的幻觉——引用真实段落，不代表结论被段落支持。

原文："小王上周提过周五上线，但现在先暂停，等测试结果。"

模型可能正确引用该段，却提取出"小王周五完成上线"。

这是 V2 的切入点：引入第二个 Agent 做语义层面的证据裁决，并把"核验到底改善了多少"做成可量化的工程故事。

---

## 三、功能优先级

### P0：评估基线数据集建设（最先做）

链路已验收，但 1–2 个样本只能证明"能跑通"，不能证明"质量如何"。V2 的所有对照实验都需要一个有代表性、有人工标注的基线数据集作为分母。

要做的：

1. 扩充样本到 8–12 场真实会议，覆盖 V1 已跑过的会议加新样本，重点覆盖边界类型：取消承诺、条件承诺、日期变更、同名人员、跨段指代、证据不足、负责人不明确。

2. 人工标注 golden set：每场会议标注"应该提取出的行动项集合"、每条行动项的证据支持关系、负责人/日期的正确值。

3. 划分开发集与保留测试集（如 70/30），保留集不参与调参，只用于最终回归。

4. 跑 V1 单次提取在这套数据集上的指标，作为 V2 对照基线：提取准确率/召回率、字段正确率、证据支持率、幻觉率、端到端延迟、token、调用次数。

5. 确认 LangSmith 收到节点追踪与 token 上报，并把 run\_id、输入版本、模型/prompt 版本、节点耗时、token 记入可查询记录。

产出：一份 V1 基线指标表 \+ 一套可复用的标注数据集。后续所有"改善了 X%"都以它为分母。

> 为什么这一步不能被 P1 替代：如果先做核验 Agent 再补数据集，你会不自觉地把数据集往"核验 Agent 表现好"的方向标注，评估就失去独立性。基线必须先行。
> 
> 

---

### P1：双 Agent 证据裁决 \+ 有上限的修正循环（核心）

#### 角色设计

核验覆盖四类问题：承诺是否成立、是否被后文取消、负责人是否明确、日期与验收条件是否被编造。

#### 关键设计约束

1. 核验 Agent 必须能访问原始上下文，不能只读提取结果，否则会沿用提取阶段的错误。

2. 有上限的修正循环：核验失败 → 携带核验反馈回到提取节点 → 最多修正 1 次 → 仍无法确定则标记"证据不足"，交人工重点审查，不阻塞流程。

3. LangGraph 条件边实现：提取节点 → 路由到核验节点 → 通过则继续，不通过回提取（带反馈，计数上限）→ 超限转人工。或者你自己觉得合适的多智能体方案

#### 双模型策略（成本\-延迟\-质量权衡）

- 提取用能力较强的模型保召回

- 核验用成本更低/速度更快的模型做大部分筛查，边界模糊时升级到强模型

- 面试讲"权衡"的绝佳素材，也直接对应性能优化

---

### P2：评估闭环与递进对照实验（与 P1 同步）

P1 每完成一版，就在 P0 的数据集上跑评估。

#### 递进对照实验（最有价值的产出）

V1 单次提取 → 增加核验 → 增加受控修正，三组配置在同一数据集、同一模型与配置下比较：

- 质量收益：证据支持率、幻觉率变化

- 漏提风险：召回率是否因核验误拦截而下降

- 额外成本：调用次数、token、延迟增量

关键样本必须有人工作为依据，不能只用 LLM\-as\-judge 自证系统更好。

#### 回归门禁

每次修改 prompt 或更换模型后跑一次离线回归，指标退化即阻断。面试可讲："我不是凭感觉调 prompt，有数据集、有指标、有门禁，能说出上一版和这一版差了几个百分点。"

#### 可观测记录字段

每次运行记录：运行 ID、输入版本、模型与 prompt 版本、节点耗时、token、重试次数、检索候选、核验理由、人工修改、最终同步结果。既能解释失败，也能比较方案。

---

### P3：容错与性能（测量驱动，先基线后优化）

#### 容错（V1 已有基础，补粒度）

V1 已实现：SQLite checkpointer 断点恢复、报告保存后避免重提、人工确认边界、写入前失败保留 pending、结果未知标记 uncertain 禁止自动重发、重启后中断同步转人工核实。

V2 补齐：

- 分块级结果持久化与恢复：长会议按议题/段落切块，成功分块不重复调用；某块失败只重跑该块，而非整场从头提取。这是当前最明确的恢复粒度缺口。

- 模型调用的分类重试与降级：结构化输出解析失败 → 修复 prompt 重试一次 → 仍失败降级到离线规则提取，不让整条流程中断；只读请求与模型请求分别配置退避、超时与总预算。

- 核验失败/超时的兜底：展示"未完成核验"，保留人工审核入口，不阻塞。

- 版本失效：输入、prompt、schema 版本变化后，使旧缓存与相关断点失效。

- 外部写入边界保持保守：图断点与业务数据分别持久化，不宣称外部写入 exactly\-once；节点重放需考虑副作用幂等。

#### 性能（先测量，再优化 LLM 与外部 API，存储只做必要改造）

验收同时看质量、耗时、成本三项，先建基线再定目标。面试讲"瓶颈在人工确认还是模型调用，数据说话"。

> 注意：P3 的优化目标应基于 P0 基线数据确定。1–2 个样本测出的延迟噪声很大，扩充样本后才能判断哪一环是真瓶颈。
> 
> 

---

### P4（可选）：跨会议承诺追踪的最小预留

降级为可选，不作为 V2 验收项。 完整实现需要候选检索、关联判断、5 种状态定义、变更时间线、双记录分离（滴答状态 vs 口头陈述），接近另一个子系统，与"单场会议提取"核心链路耦合弱，容易做成半成品。

V2 只做：

- 数据模型预留：`project_id`、行动项状态字段、变更记录表结构

- 一个最小 demo：识别"同一承诺日期变更"单场景（上次"小李周五交文档"→本次"改到下周二"，展示两次证据待确认）

- 不做完整状态分类、不做变更时间线 UI、不做向量检索

面试表述："预留了模型并跑通一个变更识别 demo；V2 聚焦证据质量，承诺追踪是 V3 方向。" 这是合理取舍，不是能力缺口。

---

## 四、开发顺序

1. P0 评估基线：扩样本到 8–12 场、人工标注 golden set、划分开发/保留集、跑 V1 基线指标、确认 LangSmith 记录

2. P1 证据核验双 Agent \+ 有上限修正循环：同步在 P0 数据集上评估

3. P2 递进对照实验：V1 单次 → 加核验 → 加受控修正，产出对照数据

4. P3 结合实测补容错与性能：分块恢复、并发、缓存、锁优化、存储拆表；优化目标由 P0 基线数据决定

5. （可选）P4 跨会议承诺追踪最小 demo

可观测与评估贯穿全过程，不单独作为后期阶段。

---

## 五、V2 交付标准

能用一组真实会议演示完整链路：发现行动 → 核验证据 →（可选）对比历史承诺 → 人工确认 → 可靠同步，并拿出一组对照数据说明：

- 新增核验 Agent 让证据支持率/幻觉率改善了多少

- 额外付出了多少调用次数、token、延迟

- 哪些边界样本仍会漏判，为什么

这比单纯增加 Agent 数量更有面试说服力。

---

## 六、明确不做

- OAuth 登录、账号、多租户、数据隔离、计费

- 完整跨会议承诺追踪、向量检索基线、变更时间线 UI

- 盲目更换存储引擎

一句话：先把 1–2 个样本扩成有人工标注的评估基线，再加一个独立核验 Agent，用对照数据量化它的价值，用测量驱动容错与性能，跨会议追踪只做预留。
